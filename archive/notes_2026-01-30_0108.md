# 笔记：并行 example（parallel-trigger-routing）重复触发与 E2E 计数口径

## 背景与预期（来自 `examples/parallel-trigger-routing/ralph.yml`）
- `spec_writer.triggers = ["spec.start", "spec.rejected"]`
  - 预期 job_runs：`2`（start 一次 + rejected 一次）
- `spec_reviewer.triggers = ["spec.ready"]`
  - 预期 job_runs：`2`（两次 ready：一次 reject，一次 approve）
- `spec_logger.triggers = ["spec.ready", "spec.rejected"]` 且 `instances=2`
  - 预期 job_runs：`3`（2×ready + 1×rejected；实例数不重要，重要的是总 job 次数）

## 关键澄清：什么是“运行次数”
你说的“spec_writer 启动了 2/3 次”，有两种口径，必须区分：

1. **instance 次数**：例如 `spec_writer#1` / `spec_writer#2` 这种实例数量变化。
   - 并行 autoscale 可能动态拉起新实例。
   - 所以“实例个数”不稳定，不适合作为断言依据。

2. **job 次数（推荐口径）**：每次 hat 被分配到一个 job，就算一次 run。
   - 在并行 stdout 里通常能看到 `job=<id>`。
   - **我们在 E2E 里要断言的是 job_runs**，并做 `job_id` 去重后按 hat 聚合。

## 事件链路澄清：event 文件到底给谁用
事件在 Ralph 里至少有两条不同“用途”的链路：

1. **Hat 输出事件（工作流事件）**
   - 这是你提到的：job 结束后通过 channel 传给 supervisor（例如 `HatInstanceEvent::JobCompleted`）。
   - 这类事件 **不是从文件读的**。
   - 但它们通常会被 **记录**到 `.ralph/events.jsonl`，用于调试/回放/审计。

2. **外部注入事件（`ralph emit`）**
   - `ralph emit` 会把事件写入 `.ralph/current-events` 指向的文件（通常是 `events-<run-id>.jsonl`）。
   - supervisor/event loop 会从该文件“增量读取新行”并注入到系统里。
   - 这里的读取是有 position 的（同一进程内不会反复读同一行），所以一般不需要“写回标记已消费”。

结论：
- `.ralph/events.jsonl` 更像“历史日志/排障锚点”。
- `.ralph/current-events -> events-<runid>.jsonl` 才是“外部输入事件流”。

## 已观察到的高风险误判点
- `examples/parallel-trigger-routing/.ralph/events.jsonl` 是 append-only 的历史日志。
  - 如果你多次运行 example，它会把多次 run 的事件混在一起。
  - 这会导致你看到 `spec.start` 出现多次，但那不一定是“单次 run 重复触发”。

## 待确认的根因假设（需要用单次 run 证据验证）
- H1：`ralph#1`（协调者）重复发布了 `spec.start`（starting_event 被触发多次）。
- H2：`spec_writer` 的第二版规格里不小心包含了 `"version: 1"` 字样/行，导致 reviewer 又 reject 一次。
- H3：事件解析/路由层发生重复投递（例如同一 job 完成事件被处理两次）。
- H4：completion 之后仍路由：`LOOP_COMPLETE` 出现后 supervisor 没进入收敛态（或收敛态实现缺口）。

## 下一步要拿到的“证据最小集”
- 一份单次运行的 stdout（至少包含 `LOOP_COMPLETE` 前后 50 行）
- 其中要能看到：
  - `[ralph#1:out:job=<id>] LOOP_COMPLETE`
  - `spec.start/spec.rejected/spec.ready` 相关事件的来源 instance
  - 是否在 `LOOP_COMPLETE` 后出现了新的 `job=<new_id>`
