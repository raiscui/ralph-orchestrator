## 2026-03-09 13:42:00 +0800 | 排查笔记: `parallel-trigger-routing-example` 在 completion 后出现 `Failed to send JobCompleted to supervisor`

### 现象

- 用户关注的 warning 文本只在 `crates/ralph-core/src/parallel/instance.rs` 构造。
- 动态证据显示业务链路和 completion 都已经发生:
  - `.e2e-tests/parallel-trigger-routing-example/.ralph/events.jsonl` 已出现 `spec.approved`
  - `.e2e-tests/parallel-trigger-routing-example/.ralph/session-20260309-1201.jsonl` 已出现 `LOOP_COMPLETE`
  - 同一 session 文件里已出现 `_meta.termination` 且 `reason="CompletionPromise"`
- 另一份 stdout artifact 末尾出现:
  - `HatInstance actor exited with error instance=ralph#1 error=Failed to send JobCompleted to supervisor`

### 候选假设

- 主假设:
  - `ralph#1` 的某个收尾 job 在 Supervisor 已经进入 completion/shutdown 或 receiver 已被 drop 之后,仍试图上报 `JobCompleted`。
  - 因此 `mpsc::Sender<HatInstanceEvent>` 返回 channel closed,触发 actor warning。
- 备选解释:
  - 不是 receiver drop,而是 executor error 路径(`on_job_execution_error`)触发了另一个 `JobCompleted` 发送失败。
- 推翻主假设需要的证据:
  - 找到同一 warning 实际命中 `instance.rs:1584` 的 executor error 分支,而不是 `instance.rs:1541` 的正常完成分支。

### 静态证据

- `crates/ralph-core/src/parallel/instance.rs:1494-1549`
  - `HatInstanceActor::on_job_completed()` 先 `set_state(Idle/Failed)`,后 `send(HatInstanceEvent::JobCompleted { ... })`
  - warning 字符串对应 `.context("Failed to send JobCompleted to supervisor")`
- `crates/ralph-core/src/parallel/instance.rs:150-159`
  - `actor.run().await` 返回 Err 后,外层统一打印 `HatInstance actor exited with error`
- `crates/ralph-core/src/parallel/supervisor.rs:430-543`
  - Supervisor 在看到 Ralph 的 completion promise 后进入 `CompletionPromise` 收敛态
  - 收尾只做 drain,并在满足条件时 break 退出主循环
- `crates/ralph-core/src/parallel/supervisor.rs:1232-1289`
  - `drain_shutdown()` 明确承认目标是避免 receiver 提前 drop
  - 但它只给 5 秒窗口,并且收尾阶段不再处理 `JobCompleted`
- `crates/ralph-core/src/parallel/supervisor/routing_tests.rs:1081-1083`
  - 测试注释直接写明: receiver 必须保持存活,否则 `StateChanged/JobCompleted` 会发送失败
- `crates/ralph-cli/src/parallel_runner.rs:1113-1126`
  - CLI 在拿到 `ParallelRunResult` 后,先写 `_meta.termination`,再做 `codex_*_runtime.shutdown_all()`
  - 因此 record-session 里可以先看到 completion,而外层进程仍在做 runtime cleanup
- `crates/ralph-e2e/src/executor.rs:406-414`
  - E2E 超时会直接对整个进程组发终止,这能解释最后为什么变成 timeout/exit 130

### 当前结论

- 当前更像是"completion 已达成,但退出期 receiver 生命周期和 late job completion 发生竞态"。
- 最可能的直接触发点是 `HatInstanceActor::on_job_completed()` 的正常完成路径,不是业务主链路本身。
- `exit 130` 更像外层 E2E timeout 对仍未完全退出的 `ralph run` 发了 SIGTERM,不是 completion 没有发生。

## 2026-03-09 12:28:00 +0800 | 新证据: 这是两个问题叠加,不是单一假失败

### 现象

- `.ralph/session-20260309-1201.jsonl` 明确显示:
  - `spec_writer#1`、`spec_reviewer#1`、`spec_logger#1` 都产出了后续输出
  - `ralph#1` 在第二轮 continuation 后输出了 `LOOP_COMPLETE`
  - `_meta.termination` 在 68s 就已写出,理由是 `CompletionPromise`
- 但 `.e2e/stdout.txt` 只有 449 行。
  - 里面几乎只有 `ralph#1` 的前缀输出
  - `Hat job run counts (example)` 因此只统计到 `ralph#1=1`
  - `No new jobs after LOOP_COMPLETE (example)` 也因为没看到带前缀的 `LOOP_COMPLETE` 而失败
- 进程最终仍被 E2E 300s timeout 杀掉,报告是 `exit 130`

### 主假设

- 问题不是一个,而是两个叠加:
  1. log-mode 的 child stdout 存在缓冲耐久性问题
     - observer 用 `writeln!` 写 stdout,但没有 `flush()`
     - 当 run 在 cleanup 阶段卡住并最终被 timeout 杀掉时,尾部很多并行前缀行来不及冲到 pipe
  2. 并行 run 在语义完成之后,cleanup 仍可能长时间卡住
     - `parallel_runner` 在写完 `_meta.termination` 后,还会无界等待两个 runtime 的 `shutdown_all()`

### 静态证据

- `crates/ralph-cli/src/parallel_runner.rs`
  - 日志模式 observer / state observer / initial banner / final states 都是 `writeln!` 后直接返回,没有 `flush()`
  - 这意味着在非 TTY(pipe)场景下,stdout 是否及时落到 E2E 父进程取决于缓冲时机
- `crates/ralph-cli/src/parallel_runner.rs`
  - 在 recorder 写完 `_meta.termination` 之后,直接执行:
    - `codex_mcp_runtime.shutdown_all().await`
    - `codex_app_server_runtime.shutdown_all().await`
  - 这两个等待当前是无界的
- `crates/ralph-cli/src/codex_app_server_session.rs`
  - `CodexAppServerRuntime::shutdown_all()` 会串行拿 session mutex,再 `guard.shutdown().await`
- `crates/ralph-cli/src/codex_mcp_session.rs`
  - `CodexMcpRuntime::shutdown_all()` 也是同样的无界串行 shutdown 形态

### 动态证据

- 同一轮 run 里:
  - session recorder 看到了 `spec_logger#1` 的 `stdout=true` 日志行
  - 也看到了 `spec_reviewer#1` 的 `spec.approved`
  - 还看到了 `ralph#1` 的 `LOOP_COMPLETE`
- 但 child stdout artifact 没有这些对应的带前缀行
- 这更像 stdout flush/耐久性问题,而不是业务实例根本没输出

### 当前结论

- 该场景当前至少要同时修两件事:
  - 修 child stdout 的 log-mode flush,让 E2E/人工观察拿到完整前缀证据
  - 修并行 run 的 cleanup 有界退出,避免 completion 已发生却被 300s timeout 杀掉

### 现象

### 当前主假设

- completion promise 的更合理语义应当是:
  - 仍然必须在 event payload 之外。
  - 但还要进一步收紧到“独立单行等于 promise”。

- 如果历史场景真实依赖“句中提及 token 也算完成”,收紧后会暴露旧 example / 测试 / 文档里隐含的不一致。

- 从控制面语义看,`LOOP_COMPLETE` 更像一个 out-of-band sentinel,不是自然语言说明的一部分。
- 现有并行 flaky 根因已经证明“子串命中”会误杀后续 job 派发。
- 独立单行匹配是最小改动:
  - 不需要引入新协议。
  - 不需要改 event 结构。
  - 仍兼容最直白的最终输出形态。

### 最小验证计划

- 先把 runtime 与 E2E 的 completion 检测一起收紧到单行精确匹配。
- 同步改旧测试口径:
  - 单独一行通过。
  - 普通 prose 中出现失败。
  - event payload 中出现失败。
  - 混合多行文本中,只有某一行单独等于 promise 才通过。

  - renewal 场景失败的主因是 prompt 对 event 形态约束不足。
  - 需要显式禁止 self-closing event 和 attribute-only payload,而不是先改 parser。
