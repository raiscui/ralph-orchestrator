# 任务计划: 并行 E2E 覆盖 `parallel-trigger-routing` example + 收敛与计数断言

## 目标
让并行 Tier8 E2E **直接运行** `examples/parallel-trigger-routing/ralph.yml`，并在测试里**可观测**地断言：

- `spec_writer` 的 **job_runs == 2**
- `spec_reviewer` 的 **job_runs == 2**
- `spec_logger` 的 **job_runs == 3**
- `ralph#1` 输出 `LOOP_COMPLETE` 之后，**不得再出现新的 job**（不允许 completion 后继续派工）

同时，针对你反馈的异常现象做根因分析，并给出“从根上避免重复触发”的修复方案：

- `spec_writer` 在 `LOOP_COMPLETE` 前跑了 3 次（理论上应为 2 次）
- `LOOP_COMPLETE` 后其他进程仍持续创建 job 并运行

## 方案（至少二选一）

### 方案 A：不惜代价，最佳方案（更稳、更“从根上”）
- **运行时保证**：把 `starting_event` / completion 收敛语义做成 runtime 级约束。
  - `starting_event` 只允许“新 run”时触发一次（多次触发视为错误或直接丢弃）。
  - `LOOP_COMPLETE` 一旦出现，Supervisor 进入“收敛态”：允许已在跑的 job 自然结束，但 **禁止再路由/派发任何新 job**。
- **E2E 强回归**：新增 Tier8 场景直接跑 example，并按 “job_id 去重 + hat 聚合” 做次数断言。
- 优点：稳定、可解释、不会靠 prompt “遮羞”。
- 代价：需要改 runtime 逻辑与补齐测试，改动面稍大，但能一次性把坑填平。

### 方案 B：先能用，后面再优雅（风险更高，不推荐）
- 在 E2E 场景的 prompt 里强行约束 ralph#1 “只发一次 spec.start / 不要产生第 3 次 spec_writer”。
- 优点：改动小。
- 缺点：这会“教模型别犯错”，但 **并没有从机制上防止重复触发**，更像掩盖问题。

> 默认选择：**方案 A**（因为你要求的是“追踪每个 hat should run 多少次”，且你已经观察到真实运行会漂移/失控）。

## 关键问题
1. “`spec_writer` 跑 3 次”到底是 **单次 run** 内发生，还是 **`.ralph/events.jsonl` 跨多次 run 叠加**造成的误判？
2. `starting_event=spec.start` 在并行 supervisor 模式下，是否可能被 ralph#1 重复发布？如果会，runtime 是否应该硬性去重/拒绝？
3. 你提到的“event 触发过后是否标记已用过”：当前事件系统是否已经有“消费语义”，缺口在哪里？
4. `LOOP_COMPLETE` 后仍派工：是 supervisor 路由逻辑问题，还是外部事件注入（`ralph emit`）导致？

## 做出的决定
- [决定] 以 **job_runs（按 job_id 去重）** 作为“运行次数”口径，而不是 instance 数。
  - [理由] 并行 autoscale 可能动态创建实例（例如 `spec_writer#2`），但我们关心的是“这个 hat 的工作被执行了多少次”。
