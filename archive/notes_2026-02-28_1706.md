# 笔记: E2E - Codex App Server turn/steer 多轮对话(2026-02-23)

## 目标

- 新增 Tier 8 并行 E2E: 在 `ralph#1` 的 turn 仍在 in-flight 时,注入 2 次 steer。
- 验证 steer 输入确实通过 Codex App Server 通道进入(而不是降级成普通 pending 事件)。
- 验证最终能收敛到 `LOOP_COMPLETE`。

## 关键想法

- 用一个可控的 fake codex app-server 来固定时序:
  - `turn/start` 后先输出一行提示,但不发送 `turn/completed`。
  - 只有在收到 2 次 `turn/steer` 后,才输出 `LOOP_COMPLETE` 并发送 `turn/completed`。
- E2E 侧并发执行:
  - 一边启动 `ralph run`。
  - 一边轮询 `.ralph/agents.json`,等看到 `ralph#1` 进入 `Running` 后再 `ralph emit --turn-action steer`。
  - 这样可尽量避免 steer 事件过早投递导致的“降级为普通消息入队”。

## 证据/断言口径

- stdout 中包含 fake app-server 的 stderr marker(证明走了 app-server 通道,且 stderr forward 正常)。
- stdout 中包含 2 个 steer marker(证明多轮 steer 生效)。
- `termination_reason == LOOP_COMPLETE`。
- `.e2e/human-log.md` 必须落盘且包含 marker 与关键命令(便于人类审计/排障)。

## 备注

- 该场景目标是验证 Ralph 的 turn/steer 管线闭环,不依赖真实网络,不消耗真实 Codex token。

### 发现的根因(非预期): busy ralph 改投会破坏 steer/interrupt

- 现象:
  - 第 1 次 steer(显式 target_instance=ralph#1)被改投到 ralph#2,导致 ralph#1 的 in-flight turn 没收到 steer。
  - 只有当 ralph#2 也处于 Running 时,第 2 次 steer 才会“兜底回到 ralph#1”(双忙兜底),从而出现只命中一次 marker 的假象。
- 根因:
  - `crates/ralph-core/src/parallel/supervisor/routing.rs` 的
    `rewrite_target_for_busy_ralph()` 会在 ralph#1 Running 时把显式 target_instance=ralph#1 的事件改投 ralph#2。
  - 该逻辑对“协调面普通事件”有价值,但对 turn/steer 与 turn/interrupt 属于语义破坏:
    - 它们必须直达目标实例,否则无法影响正在运行的 turn/job。
- 修复:
  - 对 `event.turn_action == Steer|Interrupt` 直接跳过改投逻辑,保持直达 ralph#1。
  - 新增单元测试锁死:
    - `busy_ralph_primary_explicit_target_is_not_redirected_for_turn_steer`
    - `busy_ralph_primary_explicit_target_is_not_redirected_for_turn_interrupt`

### E2E harness 小改良

- `crates/ralph-e2e/src/executor.rs`:
  - 新增 `run_with_extra_env()`: 仅对 ralph 子进程注入 env(用于 PATH 注入 fake codex)。
  - 避免在测试进程里使用 `std::env::set_var/remove_var`(当前工具链下为 unsafe,且本仓库 forbid unsafe)。

## 2026-02-23 23:05 +0800 | Codex app-server: real vs fake 协议差异 + steer 时序修复

### 背景

- 已有确定性(fake)回归场景: `parallel-app-server-steer-multi-turn`.
- 新增真实(live)场景: `parallel-app-server-steer-multi-turn-live`.
- 目标是用“真实 codex app-server”验证:
  - `turn/steer` in-flight 注入可用.
  - 能收到 app-server 的 response 回执.
  - 运行能收敛退出(完成信号 + completion_promise).

### 关键差异(协议层)

#### 1) 输出通道差异

- fake app-server:
  - 主要输出: `item/agentMessage/delta`
  - 完成信号: `turn/completed`
- real codex app-server(实测 codex-cli 0.105.0-alpha.13):
  - 会出现两类输出相关 notify:
    - `item/reasoning/summaryTextDelta`(reasoning 摘要,高频)
    - `item/agentMessage/delta`(真正 agent message 输出,通常在后段出现)

结论:
- `item/reasoning/summaryTextDelta` 不能当成唯一“完成依据”,否则容易出现:
  - 只是在描述“我将要输出 completion_promise”,但并未真正输出.
  - completion_promise 被误触发(因为 contains substring).

#### 2) 完成信号差异

- fake app-server:
  - 用 `turn/completed` 做 job 完成信号.
- real codex app-server:
  - 观察到 `codex/event/task_complete` 出现,但不稳定观察到 `turn/completed`.

结论:
- `CodexAppServerRuntime` 需要把 `codex/event/task_complete|task_completed` 视为 turn 完成信号的兼容路径.

#### 3) steer 的时序门槛差异(最关键)

现象:
- 在 real codex app-server 下,过早发送 `turn/steer` 会返回 error:
  - error_code: `-32600`
  - error_message: `"no active turn to steer"`

推断(结合 trace):
- `turn/started` 到达并不等价于“turn 已进入可 steer 的 active 状态”.
- 更可靠的门槛是 `codex/event/task_started`(模型任务真正开始跑).

修复策略:
- 收到 steer 控制信号后:
  - 优先等到 `codex/event/task_started` 再 flush `pending_steers`.
  - 同时加 2s 兜底,避免某些版本不发 task_started 导致永远不 flush.

### 工程修复点(代码层)

- `crates/ralph-cli/src/codex_app_server_session.rs`
  - trace: 兼容 JSON-RPC error response(原先只记录 result response).
  - trace: 增大 stderr broadcast buffer(避免高频 delta 下 trace 行丢失,影响人类审计).
  - completion: 增加 `codex/event/task_complete|task_completed` 作为完成信号.
  - steer: 等 `codex/event/task_started` 后再发送(否则可能 "no active turn to steer").

- `crates/ralph-e2e/src/scenarios/parallel/app_server_steer_multi_turn_live.rs`
  - 断言增强:
    - steer 不仅要 send>=2,还要 recv response>=2.
    - response 需要是成功回执(不能包含 error_code).
    - 必须看到 `[ralph#1:out:job=...]`(证明 stdout 输出通道可用).
  - human-log.md 增强:
    - 增加“精选(握手 + steer 回执)”小段,避免淹没在长 trace 里.

### 当前结果

- fake 场景 PASS: `parallel-app-server-steer-multi-turn`.
- live 场景 PASS: `parallel-app-server-steer-multi-turn-live`.
- live human log 现在能直接看到:
  - `turn/steer` send 两次.
  - `turn/steer` recv response 两次(成功).
  - 最终收敛退出(exit_code=0,termination_reason=LOOP_COMPLETE).

## 2026-02-24 09:56 +0800 | 追加: “具体任务 payload”覆盖的稳定性要点

### 1) fake app-server 需要模拟 `codex/event/task_started`

- 现象:
  - 在 `CodexAppServerRuntime` 引入“steer 等待 task_started/2s”门槛后,
    fake app-server 如果只发 `turn/started` + 输出一行 `WAITING_FOR_STEER` 就进入静默,
    容易导致 steer 永远不 flush(尤其 steer 发生在前 2s 内)。
- 结论:
  - 为了让 fake 更贴近真实协议,应在 `turn/started` 后发布 `codex/event/task_started`。
  - 这样既能对齐真实语义,也能让 pending steer 在“没有额外 notify”时仍可被触发 flush。

### 2) 真实(live)场景不适合强制 question/answer 输出格式

- 现象:
  - live steer payload 注入 question 后,真实模型可能出现输出漂移:
    - 不再按 prompt 输出 `LOOP_COMPLETE`,从而在 90s 窗口内无法收敛。
- 结论:
  - live 场景更适合验证“RPC send/recv + 收敛”;
  - “任务执行/反馈(answer)”应由确定性 fake 场景与 spawn_instance 场景覆盖。

### 3) Python regex 在 Rust raw string 中不要误用双反斜杠

- 现象:
  - 把 `\d` 写成 `\\d` 会导致 regex 匹配失败,最终输出 `answer: <unknown>`。
- 结论:
  - Rust 的 raw string(`r#"... "#`)里写 Python regex,按 Python 语法直接写单反斜杠即可。

## 2026-02-24 20:02 +0800 | 结论: 真实 app-server 下 steer 不保证“同一轮立刻可见回复”,验证 answer 更适合两轮 turn

- 现象:
  - 在真实 codex app-server 下:
    - `turn/steer` 可以成功 send/recv(有 ACK)。
    - 但模型不一定会在当前 in-flight turn 里立刻输出可见 answer。
  - 如果 prompt 设计为“等 steer 才开始输出”,可能会观察到:
    - stdout 主要是 reasoning/summary 的长文本。
    - human-log 看起来像“无回复”(其实是没有进入我们期望的可见输出节奏)。

- 结论:
  - transport(ACK)证明“通道可用”。
  - 要稳定证明“steer 被消费并生成可见回复(answer)”,更可靠的做法是:
    - 第 1 轮: 明确输出 `STEER_WINDOW_OPEN`(keep-alive),只负责开窗口。
    - 第 2 轮: 用一个显式事件(例如 `e2e.reply.step2`)触发下一次 turn,再从 thread 历史读取两条 steer 输入并输出 answer。
  - 这样可以避免把“steer 能否立即打断当前输出”当成协议前提,降低 flake。

## 2026-02-25 11:06 +0800 | Parallel Idle Start(无 PROMPT.md 待机)

### 现象

- 目前 `ralph run`(串行与并行)都会在没有 prompt 时直接失败:
  - `resolve_prompt_content()` 在 prompt_file 不存在时会 `bail!`。
  - 并行模式 `run_parallel_loop_impl()` 也调用同一函数,因此在缺失 `PROMPT.md` 时无法“启动后待机”。
- 并行 Supervisor 在启动后会立刻路由 `task.start -> ralph#1`,这会触发一次真实后端 job,与“0 token 待机”冲突。

### 关键结论(需求)

- 当没有 `PROMPT.md` 且未传 `-p/-P` 时:
  - 在 codex app-server 的并行 TUI 模式下,应该允许启动后待机。
  - 待机期间不应触发任何 job,也不应该为了进入暂停态而让模型先输出 `LOOP_COMPLETE`。
- headless/CI/E2E 需要显式开关 `--idle-start`,否则默认仍应报错(避免脚本静默挂住)。
- idle_start 期间 `max_runtime_seconds` 不计时,直到第一次实例进入 Running 才开始计时。

### 代码定位

- prompt 解析入口:

## 2026-02-27 17:42 +0800 | 落地: Codex app-server runtime 的 no-output watchdog(对齐 `HatJob.timeout/output_stale_timeout`)

### 问题(为什么要做)

- 在 `session_strategy=app_server` 下:
  - job 的完成主要依赖 `turn/completed`/`codex/event/task_complete(d)` 通知。
  - 旧实现没有消费 `HatJob.timeout/output_stale_timeout`,并且 cancel 时也不会退出 job。
- 结果:
  - 某些“无输出沉默”或“缺失完成通知”的时序下,job 会无限等待。
  - instance 会长期卡在 Running,只能靠全局 max_runtime 止损,不够确定也不够可审计。

### 方案(怎么做,为什么这么做)

- 把 openclaw 的 "no-output watchdog" 思路迁移到 app-server runtime:
  - `HatJob.timeout`: 检测窗口(check interval)。
  - `HatJob.output_stale_timeout`: 输出停滞阈值。
  - tick 到期时:
    - 若输出停滞超过阈值: `timed_out=true`,best-effort `turn/interrupt`,并立即返回。
    - 若未提供 stale 阈值: 退化为“硬超时”语义。
- cancel 语义对齐其他 runner:
  - 一旦 cancel=true: best-effort `turn/interrupt`,并立即返回 `canceled=true`。
- timeout 后重启 session:
  - 从 runtime map 移除并 kill `codex app-server` 子进程。
  - 目的: 避免残留 active turn/thread 污染后续 job,把“超时”变成确定性失败。
- 附带修复:
  - 当 stderr/control/cancel 通道关闭时,禁用对应 `tokio::select!` 分支,避免 recv 立即返回导致 busy loop。
