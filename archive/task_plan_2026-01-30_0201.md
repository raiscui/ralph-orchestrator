# 任务计划: 并行 E2E 覆盖 `parallel-trigger-routing` example（计数断言 + completion 收敛）

## 目标
把你提到的 `examples/parallel-trigger-routing` 这个 demo **纳入 Tier8 E2E**，并用“可观测证据”锁死它的预期行为：

- 直接使用 example 的 `ralph.yml`（不再“自己生成一个类似配置”）
- 断言（按 **hat 聚合的 job_runs**，而不是 instance 个数）：
  - `spec_writer job_runs == 2`
  - `spec_reviewer job_runs == 2`
  - `spec_logger job_runs == 3`
- 断言：`ralph#1` 输出 `LOOP_COMPLETE` 之后 **不得再出现新的 job**（避免 completion 后仍派工、出现“假活跃”）

同时，系统化分析你描述的异常（并给出可执行解释）：

- 你看到 `spec_writer` 在 `LOOP_COMPLETE` 前跑了 3 次（预期应为 2 次）
- 你看到 `ralph#1` 发出 `LOOP_COMPLETE` 后，其他进程仍不断创建/运行 job

## 方案（至少二选一）

### 方案 A：机制兜底（推荐）
- 运行时保证：
  - completion promise（`LOOP_COMPLETE`）出现后进入“收敛态”：允许已在跑的 job 自然结束，但 **禁止再路由/派发任何新 job**。
- E2E 断言口径：
  - 使用并行 stdout 的前缀 `[instance:out|err:job=<id>]` 提取 job_id；
  - 对同一 job 的多行输出做 job_id 去重；
  - 再按 hat（`spec_writer#*`）聚合得到 job_runs。

### 方案 B：提示词压制（不推荐）
- 在 E2E prompt 里强行“教模型别触发第 3 次”，用 prompt 稳定跑通。
- 风险：掩盖机制问题；对“真实用户跑 demo”的价值较低。

> 本次选择：方案 A。

- [决定] 断言“次数”时以 **job_runs** 为准（按 job_id 去重），不以 instance 个数为准。
  - [理由] autoscale/动态实例会让 instance 数波动，但 job_runs 才是工作量/流程次数的真实度量。
