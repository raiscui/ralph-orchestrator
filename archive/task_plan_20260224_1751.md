# 任务计划: 让 autopilot/tests 可控限并发,但不影响用户 `ralph run` 默认并发(2026-02-18 18:50 +0800)

## 目标

- 在 autopilot/tests 场景下,允许通过 CLI 参数“显式约束并发”,以便:
  - 测试能稳定复现(不因并发太大而噪声/波动).
  - 需要时也能把并发压到很小,观察队列/窗口/backpressure 的效果.
- 同时保证:
  - 用户在自己项目目录里直接执行 `ralph run` 时,不会被这些“测试用并发约束”影响.
  - 换句话说,并发约束必须是 autopilot/tests 的 opt-in,不能变成全局默认行为.

  - `--child-parallel-max-running-jobs <N>`
- autopilot 在 out_dir 内生成一份派生 config(例如 `child_ralph.yml`),只用于本次 child `ralph run`.
- 用户直接 `ralph run` 不会读到这些覆盖参数,也不会产生行为变化.

### 方案B(先能用,但对使用者更手工)

# 任务计划: app_server 三种消息投递模式 + `ralph agents` 实时列表(2026-02-18 20:30 +0800)

## 目标

- 当 event 的接收方是“可持续问答”的会话(例如 Codex App Server)时,发送消息支持 3 种模式:
  1) new_instance: 立即开一个崭新实例接收消息(上下文隔离).
  2) turn: 作为新 turn 排队发送(等目标实例空闲后处理).
  3) steer: 立即把消息输入到 in-flight turn(实时 steer).

- 在 `config/all_hat.md` 给出清晰、可复制的协议指引:
  - Ralph/各 hat 如何选择 3 种模式.
  - 如何启动新智能体实例,以及如何控制已有实例(turn/steer).

- 增加 CLI 命令: `ralph agents`
  - 输出当前存在的 hat instance 列表.
  - 展示它们在做什么: 以“最后一次收到的输入(事件 topic + payload 预览)”作为概述.

- 约束:
  - 测试/工具可以限并发以便观察效果.
  - 但用户在自己项目目录里直接 `ralph run` 时,不应被默认额外限制并发.

## 两个方向(需要择一)

### 方案A(推荐,最小新增,复用既有 turn_action)

- 新增 per-event 字段/属性: `spawn_instance`(bool).
  - 当 `spawn_instance=true` 且 `target=<hat_id>` 时,路由层强制创建一个动态实例并投递给它.
  - 与现有字段组合,即可表达 3 种模式:
    - new_instance: `spawn_instance=true` + (可选)`session_strategy="app_server"`
    - turn: 默认(不写 turn_action),或 `turn_action="start"`
    - steer: `turn_action="steer"`(缺失 session_strategy 时运行时会自动升级到 app_server)

- 运行态落盘: 并行 Supervisor 在 `.ralph/agents.json` 维护“实例状态快照”.
  - `ralph agents` 只读该文件并展示.

优点:
- 新增字段最少,不重复发明 turn_action.
- 对现有事件语义影响小.

风险:
- 需要在文档里把“3 种模式 = 1 个新字段 + 现有 turn_action”讲清楚.

### 方案B(更统一,但新增更大)

- 新增高层字段: `message_mode=new_instance|turn|steer`.
  - 由解析层把它翻译成底层 `spawn_instance/turn_action/session_strategy`.

优点:
- 对 hat 作者更直观(只选 1 个字段).

风险:
- 与现有 `turn_action` 语义重叠,需要处理冲突/优先级.
- 代码面与文档面都更复杂.

- [决定] 选择方案A.
  - [理由] 改良胜过新增.我们只补齐“缺的那一块”(显式开新实例),其余复用已存在的 turn_action/steer 语义.
